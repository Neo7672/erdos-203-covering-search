# Erdos problem #203 / JSP-000190 - covering-system attack (unfinished)

**Status: NOT SOLVED.** This repository documents a complete machine-assisted
attack on the problem, the infrastructure built for it, and the precise reason
it did not converge. Published so the work is reusable rather than lost.

Related: [erdosproblems.com #203](https://www.erdosproblems.com/203) (open),
entry **JSP-000190** of [The Justin Sun Prize](https://github.com/TheJustinSunPrize/awards).

## The problem

> Is there an integer m with gcd(m, 6) = 1 such that none of
> m * 2^k * 3^l + 1 are prime, for any k, l >= 0?

Equivalently: does a **Sierpinski number for the two-base sequence 2^k 3^l**
exist? (78557 is the classical Sierpinski number for 2^k alone.)

## Method: covering systems on the lattice Z^2

Fix m. For a prime p, the set of (k, l) with p | m * 2^k * 3^l + 1 is determined
by the residue of m modulo p. Inside the multiplicative group generated by 2 and
3 mod p - cyclic of order

    h(p) = lcm(ord_p(2), ord_p(3))

- the covering condition becomes a **linear congruence**

        alpha*k + beta*l = c  (mod h(p))

  where 2 = g^alpha, 3 = g^beta for a generator g of <2, 3>, and c is fixed by
  m = -g^(-c) mod p.

Each usable prime therefore contributes **one coset of an index-h(p) sublattice
of Z^2**, i.e. density **1 / h(p)** of the lattice. If a finite set of primes has
cosets whose union is all of Z^2, the corresponding m (Chinese remainder
theorem) makes m*2^k*3^l + 1 composite for every k, l - solving the problem.

## What was built

| file | role |
|---|---|
| `search203.py` | enumerates every prime with h(p) <= 400 (and, in a second pass, all primes with h(p) dividing a target M), computes ord_p(2), ord_p(3), the generator g and the discrete logs (alpha, beta) |
| `cover_lns.py` | LNS (large-neighbourhood search) over the torus (Z/M)^2; maintains a coverage-count array and repeatedly ruins/reinserts cosets |
| `cover_lns_band.py` | same, banded, for large M (memory-limited) |
| `inventory_full.json` | the prime inventory |
| `verify203.py` | independent re-verification: prime data, full-torus cover check, CRT construction of m, end-to-end spot checks |

## Prime inventory (complete)

Scanning all primes below 5,000,000: **105 primes** have h(p) <= 400, and the
total available density

    sum_p 1/h(p)

is about **1.63** over that set (it diverges slowly, like log log, as h grows),
so covering systems are not excluded by a density obstruction. For a fixed torus
size M only primes with h(p) | M can be used, which caps the budget:

| M | usable primes | budget | torus cells | memory for the count array |
|---|---|---|---|---|
| 5040 | 31 | 1.0214 | 25.4 M | 25 MB |
| 27720 | 29 | 1.0451 | 768 M | 768 MB |
| 55440 | 37 | 1.1495 | 3074 M | 3.07 GB |

## Why it did not converge

The LNS plateaus at roughly **17-21% of the torus uncovered** (M = 5040 and
M = 27720), and does not approach 0. The reason is structural, not a lack of
compute:

* the budget surplus (budget - 1, i.e. the overlap one is allowed to waste) is
  only 2-15%, whereas two cosets of **transverse** lattices always intersect
  (density 1/(h_i h_j)), giving a forced pairwise waste of order 0.4;
* disjointness between two cosets is possible only when their linear forms are
  proportional modulo gcd(h_i, h_j) - which is rare in this prime set. Effectively
  the only nesting found is K_5 contains K_97 (h = 4, 48, forms proportional mod 4);
* the uncovered set is spread **uniformly** across rows and columns (measured
  std/mean ~ 0.17), so no row-wise or column-wise decomposition rescues it.

Conclusion: the missing ingredient is a **structural** covering design (e.g. a
hierarchical/nested family), not more search time. The 1D Sierpinski covering
(78557) works because congruence classes there nest cleanly; the diagonal
lattices here mostly do not.

## Reproducing

```bash
python search203.py 5000000          # builds inventory_full.json
python cover_lns.py 5040 12 1        # LNS on (Z/5040)^2 for 12 minutes
```

Requires numpy and sympy. The banded engine (`cover_lns_band.py`) takes the same
arguments but processes the torus in bands for large M (memory bound: on an 8 GB
machine M = 55440 ran out of memory).

## Honest summary

* No m was found; the problem remains **open**.
* The reduction to a 2D covering-system search, the complete prime inventory with
  discrete-log data, and the budget/structure analysis above are, as far as this
  author knows, a clean statement of what any covering-system approach must
  overcome.
